# GitHub Project Operations

Use `bun scripts/github-project.ts`; statuses are `todo`, `in-progress`, `review`, `done`, or `blocked`. `blocked` means the task requires a human decision, not merely that it has dependency links. Move a task with `move --status blocked --body` containing `## Question`, `## Options`, and `## Recommendation`; the helper adds that body as the issue comment before changing the status. Use `blocked` to list human-blocked tasks and `dependency-blocked` to list tasks with dependency links. Use `ready`, not raw `gh` pipelines. Use `create`, `comment`, and `validate-delivery` for project auditability. Use `pr-status --pr <number-or-url>` for lifecycle state and `pr-checks --pr <number-or-url>` for the complete check rollup. Create a PR only through `pr-create --title <title> --body <body> [--base <branch>] [--head <branch>]`. Merge only through `merge --issue <number> --pr <number-or-url> --review-verdict approve`; enable GitHub auto-merge only through `auto-merge --pr <number-or-url> --review-verdict approve`. Both commands always use squash and reject a supplied `--method`; merge also enforces the open, non-draft, committed, clean, passing-check, linked-issue, project-`review`, and explicit local Hunk approval gates. Never use raw `gh` commands for project or PR operations. For review, use the project `hunk-review` skill: `sm` starts and owns the loopback daemon plus PTY-backed session, reviewers inspect that session and add local Conventional Comments, and `request-changes` returns the task to `in-progress` with the complete `hunk session comment list --type all` output handed to the original implementation agent. Do not ask a user to launch Hunk or replace local review comments with GitHub comments. Project JSON is `{ items, totalCount }`, defaults to 30, and item IDs differ from issue numbers. Discover options dynamically. Drafts are not issues. Run `reconcile` after writes. `review` requires commit + PR; `done` requires QA + merge.
